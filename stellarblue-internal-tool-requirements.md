# StellarBlue Internal Tool — Requirements

**Working name:** Orbit (placeholder)
**Stack:** Next.js (App Router) on Vercel · Supabase (Postgres, Auth, Storage, RLS)

---

## 1. Purpose & scope

An internal admin tool for StellarBlue covering four domains:

1. **Compensation & payment tracking** — what each person costs, what was paid, when.
2. **Leave management** — requests, approvals, balances.
3. **Remote work tracking** — who works from where, against policy.
4. **Contract management** — registry for client *and* supplier/vendor contracts with renewal/notice alerting.

**Sizing:** 11 people today, ~20 within 24 months. This is a small-N tool. Every design decision should favour *speed of change* over scalability. There is no performance problem at this size; there is a maintenance problem if the schema is over-engineered.

### 1.1 Explicit non-goals

| Not building | Why | Stays with |
|---|---|---|
| Gross-to-net payroll calculation | ΕΦΚΑ brackets, ΦΜΥ, ΑΠΔ — high-churn regulatory logic | Accountant / payroll provider |
| ΕΡΓΑΝΗ submissions (Ε11, τηλεργασία) | Legal filing channel, not replicable | Accountant, via ΕΡΓΑΝΗ ΙΙ |
| Invoicing / ΑΑΔΕ myDATA | Separate compliance surface | Accounting software |
| Expense claims, assets, performance reviews | Scope creep; revisit after v1 | — |

**Critical framing:** for leave and remote work, ΕΡΓΑΝΗ remains the legal source of truth. This tool is a *convenience and visibility layer*. The main risk is drift — the app says "approved" but nothing was ever filed. Two mitigations: every leave/remote record carries an explicit `ergani_status` field, and a **reconciliation import** (§3.7) matches internal records against ΕΡΓΑΝΗ's own export of submitted forms, so drift is detected rather than assumed away.

**Multi-entity:** explicitly out. This tool covers StellarBlue employees and StellarBlue contracts only — it will never cover Eunice JV staff. No `entity_id`, no tenancy abstraction. If that ever changes, it's a new requirement, not a latent one.

## 2. Users & roles

| Role | Who | Capabilities |
|---|---|---|
| `employee` | Everyone | Own profile, own leave requests + balance, own remote log, team leave calendar (who's out, no reasons), **no** access to any compensation data |
| `admin` | Founders | Everything: compensation, all leave approvals, contracts, ΕΡΓΑΝΗ reconciliation, settings, audit log |

**Decision:** all approvals route to the founders, so there is no `manager` role in v1. Keep roles in a `user_roles` table anyway (additive, one row per role) — adding a `manager` role later is then a policy addition, not a schema migration.

**Accountant:** no login. Monthly CSV/XLSX export of the payment ledger and contract values, generated by an admin. Keeps the auth system free of external users.

**Auth: Microsoft Entra ID SSO** via Supabase Auth's Azure provider (OIDC), restricted to the StellarBlue tenant (`tid` claim validated — not just email domain, which is spoofable across tenants). No password login, no public sign-up. First login auto-links to a pre-provisioned profile by work email; unknown users are rejected. Employee offboarding = disable in Entra ID, which kills app access at the door.

## 3. Functional requirements

### 3.1 People (foundation module)

Every other module joins to this. Build it first.

- Employee directory: name (GR + EN spelling), personal + work email, phone, role/title, team, manager, start date, end date, photo.
- **Employment type** — this matters in the Greek context and affects everything downstream:
  - `full_time` (μισθωτός, ΙΚΑ/ΕΦΚΑ)
  - `part_time`
  - `contractor` (μπλοκάκι — invoices the company, no leave accrual, no 14th salary logic). **Decision:** contractors appear *only* in the directory and payment ledger. Leave, remote, and entitlement modules skip them entirely (filtered by employment type), and their UI hides those sections.
  - `intern` / `phd_affiliate`
- Sensitive fields (ΑΦΜ, ΑΜΚΑ, ΑΜΑ ΕΦΚΑ, IBAN, address, birth date) live in a **separate table** with its own RLS policy — admin-only. Not on the profile row that employees can read about each other.
- Soft-delete only (`status: active | on_leave | departed`). Never hard-delete a person; ledger and leave history must remain intact.

**Acceptance:** an employee can view the directory and see colleagues' name, title, team, work email, manager — and nothing else.

### 3.2 Compensation & payment ledger

Two distinct concepts, often conflated. Keep them separate.

**(a) Salary history** — what someone is *contracted* to earn.
- Effective-dated rows: `employee_id`, `valid_from`, `valid_to` (null = current), gross monthly, currency, employer-cost multiplier or absolute employer contribution, notes (e.g. "annual review 2026").
- Never update in place — insert a new row and close the previous one. This gives you salary history for free and makes historical burn reconstructible.
- Contractors: store day rate or monthly fee instead of gross salary; flag with a `basis` column (`monthly_gross` | `daily_rate` | `fixed_fee`).

**(b) Payment ledger** — what was *actually paid*.
- One row per payment: `employee_id`, `period` (YYYY-MM), `payment_type`, gross, net, employer contributions, total company cost, payment date, bank reference, status (`planned | paid`).
- `payment_type` must include the Greek 14-salary reality: `salary`, `dwro_xristougennwn`, `dwro_pasxa`, `epidoma_adeias`, `bonus`, `overtime`, `contractor_invoice`, `severance`, `other`. A pure 12×monthly model will be wrong by February.
- Bulk entry: generate a draft month for all active employees from current salary history, then adjust and mark paid. Monthly data entry should take under five minutes.
- Import path: CSV upload matching the accountant's payroll export, mapped by ΑΦΜ or employee code.

**Reporting (the actual reason this module exists):**
- Monthly total company cost, by team and by employment type.
- 12-month forward burn projection from current salary history (including expected 13th/14th and holiday allowance).
- Per-employee compensation history.
- CSV/XLSX export of any of the above.

**Acceptance:** an admin can answer "what is our fully-loaded monthly cost today, and what will it be in Q2 2027 at planned headcount" without opening a spreadsheet.

### 3.3 Leave management

- **Leave types** (configurable table, not a hardcoded enum): κανονική άδεια (annual), αναρρωτική (sick), άνευ αποδοχών (unpaid), μητρότητας/πατρότητας, γονική, ειδικές άδειες (γάμου, αιμοδοσίας, φοιτητική, πένθους). Each type carries: counts against balance (y/n), requires document (y/n), requires approval (y/n), colour.
- **Requests:** date range, half-day support (morning/afternoon), optional note, attachment (sick note) to Supabase Storage.
- **Approval:** single-step — any admin (founder) approves. Requests appear in a shared admin queue; whoever acts first decides. No routing logic, no delegation chains.
- **Balances:** entitlement per employee per year, days taken, days pending, remaining, carry-over from prior year with an expiry date.
  - ⚠️ Do **not** hardcode Greek annual leave accrual rules (they vary by tenure, 5- vs 6-day week, and first-year proration). Make `annual_entitlement_days` an editable per-employee-per-year field, seeded by the accountant. A wrong auto-calculation is worse than a manual number.
- **Greek public holidays** pre-loaded per year, including movable feasts (Καθαρά Δευτέρα, Μεγάλη Παρασκευή, Πάσχα, Αγίου Πνεύματος) and the Thessaloniki local holiday (Αγίου Δημητρίου, 26 Oct). Excluded from working-day counts.
- **Team calendar:** month view, who is out, colour-coded by type. Reasons and documents hidden from non-managers.
- **ΕΡΓΑΝΗ tracking:** `ergani_status` (`not_required | pending | submitted`), `ergani_submitted_at`, `ergani_note`. Admin dashboard widget: "N approved leaves not yet marked submitted."
- **Notifications:** email on request submitted (to manager), on decision (to employee). Weekly digest of pending approvals.

**Acceptance:** an employee submits a request in under 30 seconds; a manager approves from an email link; the balance updates immediately; an admin can list everything approved but not yet filed.

### 3.4 Remote work

Deliberately lightweight — this should feel like a log, not a bureaucracy.

- Employee marks days as `office | remote_gr | remote_abroad`, either individually or as a recurring weekly default (e.g. "remote every Tuesday and Thursday").
- Optional location field, **required** when `remote_abroad` — this is the case with real tax/social-security implications, and it should be conspicuous rather than buried.
- Policy quota per employee or per team (e.g. max 8 remote days/month), with a soft warning on exceed, not a hard block.
- Team view: who's in the office today/this week.
- Same `ergani_status` pattern for τηλεργασία declarations.
- Monthly summary export: remote days per person.

**Acceptance:** setting a recurring remote pattern takes one interaction and doesn't require touching it again.

### 3.5 Contracts (client + supplier)

The module with the clearest ROI — nothing off-the-shelf knows this domain.

**Scope decision:** both sides of the ledger. Client contracts (Atlas ETRM, EMS, consulting) and supplier/vendor contracts (cloud infrastructure, data providers, PowerBot/Volue-type partnerships, office lease, insurance). Same schema; a `direction` field (`revenue | cost`) drives which views and reports each contract appears in. Notice-period alerting is equally valuable on both sides — an auto-renewing supplier contract with a missed cancellation window is a direct cost.

**Contract record:**
- Counterparty: legal name, ΑΦΜ, ΔΟΥ, country, address, contact person(s) + email.
- Contract: internal reference, type (`saas_subscription | licence | professional_services | pilot | nda | dpa | framework | jv_agreement | supplier`), status (`draft | in_negotiation | active | expiring | expired | terminated`).
- Dates: signature, effective start, end, **auto-renewal** (y/n), renewal term (months), **notice period** (days) — the notice deadline is a derived, indexed column, not something a human computes.
- Commercials: total value, currency, billing cadence (`monthly | quarterly | annual | milestone | one_off`), VAT treatment (domestic 24% / intra-EU reverse charge / non-EU), indexation clause (y/n + basis).
- Ownership: internal owner (employee), linked product (Atlas ETRM / EMS / Bidding Optimizer / consulting), linked parent contract (for amendments, SOWs, addenda — self-referencing FK).
- Documents: PDF uploads to Supabase Storage, versioned, with signature status.
- Free-text notes + key-clause flags: exclusivity, IP assignment, liability cap, data-processing terms, termination for convenience.

**Alerting — the feature that justifies the module:**
- Renewal approaching: 90 / 60 / 30 days.
- **Notice window closing** — the expensive one to miss on an auto-renewing contract.
- Contract expired while billing schedule continues.
- Contract in `in_negotiation` with no activity for 30 days.
- Delivery: email to contract owner + admins; in-app dashboard; optional Slack webhook.

**Views:**
- Pipeline board by status.
- Timeline / Gantt of active contracts.
- Revenue view: contracted client value by month over the next 12–24 months (ARR-ish, derived from billing cadence). Mirror cost view for supplier contracts — committed vendor spend per month. Net view optional.
- Filter by counterparty, product, owner, value, expiry window.

**Acceptance:** on any given day the dashboard shows every contract needing action in the next 90 days, and no notice deadline can pass unnoticed.

### 3.6 ΕΡΓΑΝΗ reconciliation (read-only validation)

**Goal:** verify that every internally-approved leave and remote-work record was actually filed in ΕΡΓΑΝΗ — without this tool ever becoming a submission channel. ΕΡΓΑΝΗ stays the legal source of truth; this module only detects drift.

**Constraint that shapes the design:** ΕΡΓΑΝΗ ΙΙ exposes a Web API for automated *submission* by third-party systems (what payroll vendors use), but there is no general-purpose read/query API for retrieving filed forms. So live sync is off the table; validation works from ΕΡΓΑΝΗ's own exports.

**Workflow:**
1. Admin (or accountant) exports the submitted-forms list from the ΕΡΓΑΝΗ portal — Ε11/annual leave and τηλεργασία declarations — as Excel/CSV, on a monthly cadence.
2. Admin uploads the file to the app. Parser tolerates the portal's format quirks; column mapping saved after first import.
3. Matching engine pairs ΕΡΓΑΝΗ rows to internal records by **ΑΦΜ + form type + date range** (with configurable date tolerance, since filings sometimes aggregate or split ranges).
4. Outcomes per internal record: `matched` (auto-sets `ergani_status = submitted` with the filing reference), `missing_in_ergani` (approved internally, nothing filed — the drift case), and per ΕΡΓΑΝΗ row: `missing_internally` (filed but never entered in the app — reverse drift, also worth seeing).
5. Reconciliation report per run: match rate, exceptions list, one-click acknowledge/resolve per exception. History of runs kept.

**Dashboard:** "last reconciliation: {date}, {n} unresolved exceptions" — stale reconciliation (>45 days) is itself a warning state.

**Future-proofing:** ingestion goes through an adapter interface, so if ΕΡΓΑΝΗ ever exposes a usable read API (or the accountant's payroll software can push a feed), the manual upload is swapped for an automated pull without touching the matching engine. **Action item:** confirm with the accountant's payroll vendor what ΕΡΓΑΝΗ ΙΙ integration surface they have today — this area changes frequently.

**Acceptance:** after a monthly import, an admin can state with evidence "everything we approved in June was filed" or see exactly which records were not.

### 3.7 Cross-cutting

- **Dashboard (role-aware):** admin sees monthly cost, headcount, pending approvals, contract alerts (both directions), ΕΡΓΑΝΗ reconciliation status + unresolved exceptions. Employee sees own balance, upcoming leave, team out-of-office, own remote pattern.
- **Accountant export:** one admin action produces the monthly package — payment ledger CSV/XLSX for the period + active contract values. No accountant login exists.
- **Audit log:** append-only. Every write to compensation, contracts, and leave decisions records actor, timestamp, table, row, before/after JSONB. Non-negotiable for salary data.
- **Global search:** people, contracts, counterparties. `⌘K`.
- **Export:** CSV/XLSX from every table view.
- **Language:** English UI, Greek data. Field labels may carry Greek terms where the Greek is the real term (Δώρο Χριστουγέννων, ΑΦΜ, ΕΡΓΑΝΗ). Full i18n is not worth it for 20 internal users.

## 4. Non-functional requirements

### 4.1 Security — the thing to get right

Salary data is the highest-sensitivity asset in this app. A misconfigured RLS policy exposes every colleague's pay to every colleague.

- **RLS on every table, no exceptions.** Default-deny; policies added explicitly.
- **Compensation tables are never read with the anon key from the browser.** Access exclusively through Next.js server actions / route handlers using the service role, with role checks in application code *and* RLS as the second layer. Two independent gates.
- Sensitive personal data (ΑΦΜ, ΑΜΚΑ, IBAN) in a separate table, admin-only policy, and excluded from any generic export.
- Storage buckets private; access only via short-lived signed URLs generated server-side after an authorisation check. Sick notes and signed contracts must never sit behind a guessable public URL.
- Entra ID SSO restricted to the StellarBlue tenant (`tid` claim validation); no local passwords; no public sign-up; access revocation happens at the IdP.
- Secrets in Vercel environment variables. Service role key never reaches the client bundle — enforce with a lint rule or CI grep on `NEXT_PUBLIC_`.

**Test requirement:** an automated RLS test suite that logs in as each role and asserts the expected 200/403 on every table. Run in CI. This is the single highest-value test in the project.

### 4.2 Data protection (GDPR)

- Lawful basis and retention documented per data category (employment records typically retained several years post-departure under Greek labour and tax law — confirm the exact periods with the accountant).
- Departed employees: profile archived, sensitive fields purgeable on a schedule, ledger history retained for accounting.
- Data export for a subject access request: one admin action producing everything held about a person.
- Since this processes employee personal data, it should appear in StellarBlue's record of processing activities.

### 4.3 Operational

- **Backups:** Supabase automated backups plus a weekly `pg_dump` to independent storage. Restore tested at least once — an untested backup is a hypothesis.
- **Environments:** local → preview (Vercel per-PR) → production. Separate Supabase projects for staging and production. Never point preview at production data.
- **Migrations:** versioned SQL in the repo (Supabase CLI), applied through CI. No changes made in the Supabase dashboard.
- **Availability:** no formal SLA. Internal tool; an hour of downtime is an inconvenience.
- **Scale:** ~20 users, low thousands of rows. Any correctly-indexed schema is fast. Optimise for readability.

### 4.4 Design

Requirement, not decoration — an ugly internal tool doesn't get used, and people fall back to spreadsheets.

- Tailwind + shadcn/ui, with a genuine visual identity rather than default shadcn slate. Pull accent colour and type from the StellarBlue brand so it feels like a StellarBlue product.
- Dense, keyboard-friendly tables. This is an operator tool: sort, filter, inline edit, bulk select, `⌘K` navigation.
- Optimistic UI on every mutation. No full-page reloads.
- Dark mode.
- Responsive down to mobile for the read paths that actually matter on a phone: submit leave, approve leave, check who's out. Contract editing and the payment ledger can be desktop-only.
- Empty states that explain what goes in the table.

## 6. Architecture

- **Frontend/backend:** Next.js App Router on Vercel. Server Components for reads, Server Actions for writes. No separate API tier.
- **Database:** Supabase Postgres. RLS everywhere. Supabase CLI migrations in the repo.
- **Auth:** Supabase Auth with the Azure (Microsoft Entra ID) OIDC provider, single-tenant. App-side middleware validates the tenant claim and maps the Entra user to a pre-provisioned profile.
- **Files:** Supabase Storage, private buckets, signed URLs.
- **Scheduled jobs:** Vercel Cron — nightly contract-alert scan, leave-carryover rollover on 1 Jan, weekly pending-approvals digest, weekly ΕΡΓΑΝΗ-gap report.
- **Email:** Resend (or Supabase's provider) with React Email templates.
- **Optional:** Slack webhook for contract alerts and leave approvals — likely higher adoption than in-app notifications.

## 7. Delivery plan

| Phase | Scope | Rough effort |
|---|---|---|
| **0 — Foundation** | Repo, Supabase projects, Entra ID SSO + tenant validation, roles, RLS scaffolding + test suite, layout/design system, audit triggers | 1 week |
| **1 — People** | Directory, profiles, sensitive-data table, teams, admin CRUD, manual initial data entry (all 11) | 3–4 days |
| **2 — Contracts** | Full module (client + supplier), alerting, cron, dashboard, manual import of existing contracts. *Highest ROI — ship first after foundations* | 1.5–2 weeks |
| **3 — Leave** | Types, entitlements, requests, admin-queue approvals, calendar, holidays, `ergani_status`, email | 2 weeks |
| **4 — Remote** | Day logging, patterns, policies, team view. Reuses phase 3 primitives | 4–5 days |
| **5 — Compensation** | Salary history, payment ledger, bulk generation, payroll CSV import, burn reporting, accountant export package | 1.5 weeks |
| **6 — ΕΡΓΑΝΗ reconciliation** | Portal-export upload, parser + column mapping, matching engine, exceptions workflow, dashboard widget | 1 week |
| **7 — Polish** | Dashboard, global search, exports, mobile paths, Slack | 1 week |

Initial data (people, balances, contracts, salary history) is entered manually during each phase's rollout — no automated migration needed. Reconciliation lands after leave/remote have accumulated a month or two of real records to reconcile against.

Sequencing rationale: contracts first because it's pure upside with no compliance entanglement and the alerting starts paying immediately. Compensation last because it's the highest-sensitivity module and benefits from the RLS patterns being battle-tested by then.

## 8. Decisions log & remaining questions

**Resolved (2026-07-30):**

| Question | Decision | Design consequence |
|---|---|---|
| Contractors | Payment ledger only | Leave/remote modules filter out `contractor`; their UI hides those sections |
| Eunice JV coverage | Never | No multi-entity design; single-tenant schema |
| Accountant access | Monthly CSV/XLSX export | No external users in auth; one-click export package |
| Existing data | Manual entry at setup | No migration tooling; phased data entry per module |
| Contract scope | Client **and** supplier | `direction` field; cost-side views and alerts |
| Approval routing | Everything to founders | No `manager` role in v1; shared admin approval queue |
| SSO provider | Microsoft Entra ID | Supabase Azure OIDC provider, single-tenant, `tid` validation |
| ΕΡΓΑΝΗ | Read-only validation desired | Reconciliation-import module (§3.6); no submission capability |

**Still open:**

1. **Leave entitlement rules:** confirm current Greek annual leave accrual and carry-over rules with the accountant before seeding the entitlements table.
2. **ΕΡΓΑΝΗ export format:** obtain a sample export of submitted forms from the portal (via the accountant) early — the parser and matching design in §3.6 depend on what those files actually contain, including whether a stable filing reference exists per record.
3. **Payroll vendor integration surface:** ask the accountant's payroll software vendor what ΕΡΓΑΝΗ ΙΙ integration they have — if their system can emit a submissions feed, the reconciliation import can be automated from day one.

## 9. Risks

| Risk | Mitigation |
|---|---|
| RLS misconfiguration exposes salaries | Automated per-role RLS test suite in CI; compensation reads server-side only |
| ΕΡΓΑΝΗ drift — app approves, nothing filed | `ergani_status` on every record + monthly reconciliation import against ΕΡΓΑΝΗ's own export (§3.6) |
| ΕΡΓΑΝΗ export format changes / lacks stable references | Adapter interface + saved column mappings; matching by ΑΦΜ + dates, not by reference alone |
| Departed employee retains access | Access controlled at Entra ID; disabling the IdP account revokes app access immediately |
| Greek labour-law rules hardcoded then change | Entitlements editable, leave types configurable, no computed accrual |
| Tool decays into an unmaintained side project | Small schema, phased delivery, each phase independently useful |
| Spreadsheet fallback because the UI is clunky | Design treated as a requirement; bulk entry and keyboard-first tables |
